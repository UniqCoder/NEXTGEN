# SANJAYA prototype audit and completion plan

Status: 28 September 2026. The acceptance baseline is the verbatim problem statement in `PRD.md` §2.1; the larger targets are in §3 and R-01–R-17. This audit describes demonstrated capability, not the intended final architecture. `PROTOTYPE_PLAN.md` is the original schedule and contains stale status labels; use this audit for current status.

Update: standalone 2/4/8-FSK noncoherent tone-bank soft demodulation and a finite-stream convolutional interleaver/inverse now have noisy, bit-exact convolutional-FEC and CRC fixtures (`engine/tests/test_fsk.py`). These operators are not yet wired into the recipe schema, blind search, proof, API, or public SITOR-B/ALE decode. The first completion gate below remains open until that integration and real-file checks are done.

UI and API hardening: the landing 3D terrain now supports drag, wheel, keyboard and reset while retaining its shaders and initial view; typography and contrast are larger; the capability scorecard and evidence scores explicitly mark unvalidated claims; a live engine result cannot acquire a proof verdict through the UI animation or demo-only expert override. A certificate now needs every proof layer to pass; missing CRC/counter evidence is not determinable and cannot certify. Receiver export requires a matching, valid signed proof as well as the bit-exact gate. The current in-memory API rejects recordings above 100 MiB before analysis. This is a safety limit, not the PRD's 8 GB streaming target.

Sample curation and sufficiency correction: the UI now offers only proof-oriented generated captures in its sample library. The short generated capture, noise control, and six public HF files remain available to tests and direct API jobs but are excluded from that menu because they cannot demonstrate the complete proof flow. The blind search no longer invents a recording-length target when no frame period or supported PHY sync is found; the MIL-STD-188-110A example explicitly reports an unresolved framing/receiver limit. A real capture may still be uploaded and measured without certification. The UI places undecided evidence above its footer and removes the disabled proof action.

## Verdict

The prototype is strong as a focused demonstration of blind BPSK/QPSK recovery and four differentiators. It does **not** yet cover the whole problem statement in its intended automated, unknown-recording sense. Several PS families work only when an analyst supplies the exact recipe. No published accuracy or false-certificate result currently justifies the PRD's numerical claims. A signed certificate proves integrity and reproducibility of its contents, while the wrong-certificate rate still requires an independent near-miss campaign.

## Distinguishing features

Layered proof, a signed re-checkable certificate, a data-sufficiency ledger, synthetic multi-sensor stitching with decoy rejection, and a gated receiver compiler all run. The compiler is tested bit-for-bit on synthetic recordings; its generated GNU Radio graph has not been executed. The sufficiency and stitching results are from generated captures, not an independently labelled real multi-sensor set. The certificate currently carries `false_pass_bound: null` and `calibration_id: v0-defaults`; do not present either as an empirical guarantee.

## Completion sequence, ordered by PS impact and error risk

1. **Close literal missing operators.** Implement 2/4/8-FSK tone-bank soft demodulation (with generated truth, noisy channels, then SITOR-B/ALE public files). Implement a convolutional interleaver and inverse. Add known-recipe end-to-end fixtures for these operators. The first gate is bit-exact round-trip plus a full decode and proof; a real file may remain undecided if its standard-specific framing/FEC is unsupported.
2. **Expand blind search without weakening certification.** Add modulation hypotheses for 8PSK then QAM, preserving all phase/bit ambiguities until CRC and proof resolve them. Add each FEC/interleaver family as a separately tested candidate generator, starting with the Meteor-M LRPT chain (RS + convolutional/diagonal or PN as required by the observed variant). Bound and record every proof attempt. A family is accepted only after blind recovery on sealed synthetic cases and an independent real capture with external-decoder agreement.
3. **Make parameter confidence real.** Build a labelled, versioned train/calibration/test corpus across SNR, duration, channel, sensor and standard; keep real capture sites and generator seeds disjoint by split. Fit calibration/conformal sets, measure 95% interval coverage, and report abstentions. Keep unknown or unsupported signals undecided. Replace any UI confidence that is merely a heuristic score with a method label and an explicit uncalibrated marker until validated.
4. **Prove error rates and speed.** Freeze thresholds before the sealed evaluation; run the preregistered 2,000,000-attempt stratified near-miss campaign and publish the binomial upper bound. Measure correct-certified and wrong-certified outcomes, per-family detection, BER/FER against independent decoder oracles, and latency/RAM on the PRD reference laptop. Repeat on real HF and satellite recordings. No numerical KPI is "met" until its sample size and interval satisfy PRD §3.5.
5. **Harden the product.** Add file-size and format limits with streaming/memory mapping, per-job process isolation/cancel/watchdog, full WAV/SigMF coverage, batch and export formats, multi-emitter detection, reconnect behavior, accessibility/performance checks, offline packaging, dependency pinning/SBOM, and Windows/Linux clean-build acceptance. Retest the four differentiators on independent real recordings.

## Immediate release gates

- A judge can select one bundled sample per claimed family and see a real measurement, decode or explicit undecided reason; no engine result may fall back to a fabricated demo value.
- Every supported PS operator has a generated truth fixture with noisy-channel tests, and each blind family has a sealed-file plus real-file test.
- A certificate with a missing, invalid or uncheckable signature is **not reproduced**. `verify` reproduces a valid one from the input recording and rejects altered files/statistics.
- The scorecard distinguishes *implemented*, *blindly identified*, *known-recipe only*, *real-file demonstrated* and *quantitatively validated* for each claim.

## Current verification

The prior full `python scripts/check.py` run passed 105 tests and the layer rule. Following sample curation and the sufficiency correction, the focused sufficiency/API checks passed, all five generated single-recording library files passed blind recovery and every proof layer, and the multi-sensor stitching suite passed 3 tests. The final UI build passes and splits the entry JavaScript to 486 kB, with a 1.01 MB terrain chunk loaded separately. This is bundle evidence, not a measured interactivity KPI. The terrain interaction has not been checked in a browser in this run.
